# AskDB logic audit — 8 October 2026

The deployed application passed 98 automated tests with live PostgreSQL checks enabled. Additional Streamlit AppTest flows used the running API and real PostgreSQL accounts. Three live Groq-generated answers were checked against direct SQL. This is a functional/code audit, not a guarantee that every possible natural-language question produces correct SQL.

## Issues corrected

| Issue | Correction and verification |
|---|---|
| Repeated SQL could replace an independent disagreement score of zero with 0.5. Even a zero agreement score could still reach the numeric success threshold. | Repeated SQL can only reduce the agreement score. Explicit disagreement always produces Needs review. A regression test returns different counts for identical SQL and verifies both conditions. |
| Reopening a clarified question discarded the chosen interpretation. Subsequent SQL edits could ask for clarification again or lose the original meaning. | Query responses persist clarification in their JSON snapshot. Reopening restores it and displays the context. Verified through the live archive UI. Older snapshots without that field cannot recover missing context. |
| Already explicit gross-revenue questions were forced through the net-revenue clarification. | Recognize explicit net/gross/discount context plus order status. Regression tests cover gross revenue from all orders and net revenue from completed orders. Ambiguous revenue still prompts before execution. |
| A generation without SQL offered an instructional placeholder as an interpretation; Continue could resubmit without supplying missing details. | Empty/single clarification requests require typed context. Multiple interpretations have no preselected choice. Continue requires a choice or additional context. Verified in AppTest. |
| A history commit failure could leave an ID for a record that was not saved. | Clear the response ID when history storage fails; retain the actionable warning. Verified by simulating a failed commit after ID assignment. |
| Scatter plots selected the same measure for X and Y by default. | Exclude the selected Y measure from X options. Verified on initial display and after changing Y. |
| A one-row, multiple-column result incorrectly claimed that a scalar metric was displayed. | Chart guidance directs the user to Data and explains that comparable records are required. |
| Duplicate selected column names could cause ambiguous SQLAlchemy mapping failures. | Stop with an actionable message asking for unique AS aliases. Verified against PostgreSQL. |
| NaN/infinity values could break JSON serialization or chart widths. | Convert non-finite database numbers to NULL with an explicit warning; omit non-finite plot coordinates. A PostgreSQL NaN regression test verifies JSON-safe output. |
| A failed transcription was marked as already processed, preventing a retry of the same audio. | Clear the digest after failure and when audio is cleared. Add Retry transcription. Unit tests verify a failed recording can subsequently succeed without running a query. |
| Feedback defaulted to Correct without an explicit choice. | Require Correct/Incorrect before saving. Verified through the live UI. |
| Results did not clearly identify the earlier question when the composer draft changed. SQL editor state could also retain an earlier unsaved result's SQL. | Display the result's question and clarification. Include the source SQL in the editor key. Verified by replacing a result without an ID. |

### Live model answers

- Sales department employees: **13**, matching case-insensitive PostgreSQL COUNT.
- Completed orders: **2,400**, matching PostgreSQL COUNT with `status = 'completed'`.
- Five most expensive products: five returned prices matched PostgreSQL `ORDER BY price DESC LIMIT 5`, verified on retry.

These answers were tagged Needs review rather than Ready. Matching these samples does not validate the model on arbitrary questions or prove semantic correctness of all JOINs. The confidence score is conservative evidence, not a probability of correctness.

The first top-products request encountered a Groq free-tier quota/rate limit; the retry later succeeded. Strict validation makes additional provider calls for meaning and independent-query checks. Rate limits can therefore interrupt queries or make validation unavailable. The app surfaces these failures and does not silently invent an answer.

## Remaining gaps

- **Live Google sign-in is not verified:** Google client credentials are not configured. The button remains disabled until setup in `docs/AUTH_SETUP.md` is completed.
- **Browser visual/input checks are not verified:** browser automation was unavailable for this localhost app. AppTest exercises server-side UI logic, but does not prove pixel layout, mobile responsiveness, contrast, animation smoothness/FPS, physical microphone permissions or native browser download behavior.
- Email verification, password reset, persistent remember-me login and linking an existing password account to Google are not implemented.
- All registered accounts share the current read-only business dataset. Personal history is private; there is no separate tenant dataset or administrator approval policy.
- Chart captions disclose that repeated labels are summed. Users must choose measures where summing is meaningful; the app cannot infer arbitrary business semantics from a column name.
